8.1 What ships with the repository

The report reads two sets of tables, both versioned in git:

output_files/consolidacion/ holds the analytical aggregates — the annual series, rates, standardised rates, sex and age breakdowns, regional and commune summaries, spatial statistics and cohort summaries that the source chapters work through.

docs/study/data/ holds the result tables the figures are built from, together with the verified facts file that the headline numbers are read from.

With these two folders, a clone can rebuild the whole report: every chapter, every table and every figure, including the panel plates, without touching the original microdata.

8.2 What a clone cannot rebuild

Two things need data that is not in the repository.

The extended plates. The 61 plates in extended material were drawn by study/pipeline/, which reads the hospital and community microdata. That code is versioned — what is missing is its input. Where a plate’s series survives in a published table, this report redraws it from that table and shows the code; where it does not, the stored image is shown and labelled as such.

The territorial maps. Commune polygons live in data/comunas.shp, which is excluded from git for its size. The maps in this report therefore need that file locally. Everything else about the territorial analysis — the rates, the ratios, the spatial statistics — comes from versioned tables.

NoteThree tables are withheld on disclosure grounds, not for size

Two commune-by-year tables and one commune-level analytic file pair a commune identifier with cells of fewer than five cases. Published together they could identify individuals. The repository ships communes_public.csv instead: the same extract without commune identifiers and with small cells masked.

8.3 Rebuilding the report

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-analysis.txt

python scripts/render_reports.py            # rebuild every chapter
python scripts/render_reports.py --figures  # also redraw the plates first

Rendering needs Quarto and Python with Jupyter, plus the scientific and geospatial stack pinned in requirements-analysis.txt. The command reads the aggregates already in the repository, so it does not require mounting the external disk — except for the maps, which read the commune shapefile.

To extract from the original microdata instead, and recompute the aggregates before rendering:

python scripts/render_reports.py --refresh

8.4 How the report keeps itself honest

Several claims in this report are checked by code rather than asserted in prose.

The figures shown are drawn by the code printed with them. The Results chapter is generated from docs/study/figuras_principales.py and figuras_suplementarias.py by scripts/build_results_chapter.py, and tests/test_page_figure_code.py fails if the code on the page stops matching the modules it came from, or if any generated chapter contains a chunk that does not parse.

The result set is one set, not a sequence of drafts. The study was written over several rounds of revision. scripts/audit_versions.py hashes every result table of every round and compares them pairwise; it reports that no table ever changed once computed, and that later rounds only ever added tables. That is why this report can present the union of all of them as a whole, and it is why the tables from the earliest analysis — on a different window and an earlier case definition — are marked apart in Result tables rather than merged in silently.

python scripts/audit_versions.py            # re-run the comparison
python -m pytest tests/                     # the guards described above
